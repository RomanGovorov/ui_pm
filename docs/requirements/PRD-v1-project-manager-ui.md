# Project Manager UI — v1

## 1. Контекст и проблема

Информация о состоянии проектов разбросана по разным каналам: электронная почта, совещания, мессенджеры. Руководители и стейкхолдеры тратят время на сборку картины из фрагментов. При этом AI-агент `project-manager` уже ведёт задачи, бэклог и статусы внутри проекта в Markdown-файлах, но у стейкхолдеров нет визуального инструмента для наблюдения за процессом.

**Почему сейчас:** агент уже работает и генерирует данные (задачи, статусы, бэклог). UI — логичный следующий шаг, чтобы сделать эту работу видимой без ручной сводки.

## 2. Цель первой версии

Создать веб-интерфейс, в котором руководители и стейкхолдеры видят актуальное состояние проекта в одном окне. Агент `project-manager` взаимодействует с UI через API и обновляет статусы задач в реальном времени.

Ключевой результат v1: **стейкхолдер открывает дашборд и видит свежие задачи; агент меняет статусы, и изменения отражаются на экране без перезагрузки.**

## 3. Целевая аудитория

| Роль | Как использует | Контекст |
|------|---------------|----------|
| **Руководитель / стейкхолдер** | Открывает UI, смотрит дашборд и канбан-доску | Хочет за 2-3 минуты понять, что происходит в проекте |
| **AI-агент project-manager** | Взаимодействует через REST API: создаёт задачи, меняет статусы, управляет бэклогом | Автоматически, без UI — через API-эндпоинты |

## 4. Пользовательский сценарий

**Основной сценарий (руководитель):**

1. Открывает дашборд в браузере
2. Видит канбан-доску с тремя колонками: **In Work → Review → Done**
3. Задачи отображаются карточками с названием, статусом, приоритетом и ответственным
4. При необходимости переключается между проектами / подпроектами через боковое меню или селектор
5. Видит, как агент обновляет статусы задач в реальном времени (без перезагрузки страницы)

**Основной сценарий (агент):**

1. Агент вызывает API для создания / обновления задач
2. Изменения мгновенно отражаются на дашборде у всех подключённых пользователей

## 5. Функциональные требования

### 5.1 Сущности

| Сущность | Описание |
|----------|----------|
| **Проект** | Верхнеуровневая единица. Содержит задачи и подпроекты |
| **Подпроект** | Группировка задач внутри проекта (опционально) |
| **Задача** | Карточка с названием, описанием, статусом, приоритетом, ответственным |
| **Пользователь** | Стейкхолдер или агент. Имеет роль и привязку к проектам |
| **Статус задачи** | `In Work` · `Review` · `Done` |

### 5.2 Дашборд

- Канбан-доска с тремя колонками: **In Work**, **Review**, **Done**
- Карточка задачи: название, приоритет (High / Medium / Low), ответственный, дата обновления
- Переключение между проектами
- Тёмная тема по умолчанию, переключение на светлую
- Real-time обновление (WebSocket / SSE) — изменения от агента видны сразу

### 5.3 API для агента

- REST API для CRUD операций с задачами, проектами, пользователями
- Эндпоинты: создание задачи, смена статуса, создание проекта, назначение ответственного
- Аутентификация через API-ключ или токен

### 5.4 Управление сущностями

- Создание / редактирование / удаление проектов и подпроектов
- Создание / редактирование задач с привязкой к проекту
- Управление пользователями и их ролями

### 5.5 UI-тема

- Тёмная тема — основная
- Переключение на светлую тему
- Стиль: минималистичный, похожий на Jira

## 6. Что не входит в первую версию

| Функция | Причина |
|---------|---------|
| Уведомления (email, push, Slack) | Вторая версия — после базового UI |
| Детальная аналитика и отчёты | Вторая версия — сначала видимость, потом аналитика |
| Drag-and-drop карточек между колонками | Агент управляет статусами через API; ручное перетаскивание — позже |
| Фильтры и поиск по задачам | Минимальный список — без сложной фильтрации |
| Интеграции с Jira / GitHub / GitLab | Не требуется для MVP |
| Мобильная адаптация | Десктопный браузер — приоритет |

## 7. Ограничения и допущения

**Допущения:**
- Агент `project-manager` уже работает и может быть адаптирован для вызовов REST API вместо прямой записи в Markdown
- Стейкхолдеры имеют доступ к десктопному браузеру
- Количество проектов и задач на старте — небольшое (до 100 задач)

**Ограничения:**
- Однопользовательский режим без ролевой модели доступа (все видят всё)
- Нет истории изменений / audit log в v1
- Нет экспорта данных

## 8. Критерии готовности

Первая версия готова к показу, когда:

- [ ] Стейкхолдер открывает дашборд и видит актуальные задачи на канбан-доске
- [ ] Агент создаёт задачу через API — она появляется на доске без перезагрузки
- [ ] Агент меняет статус задачи через API — карточка перемещается в нужную колонку в реальном времени
- [ ] Работает переключение между проектами
- [ ] Тёмная тема применяется по умолчанию
- [ ] API документирован (OpenAPI / Swagger)

## 9. Закрытые вопросы (решения)

| Вопрос | Решение |
|--------|---------|
| Синхронизация агента с UI | Агент дублирует: пишет в Markdown для внутренней работы и параллельно вызывает REST API для обновления UI |
| Стек технологий | Next.js + PostgreSQL + Prisma + WebSocket/SSE для real-time |
| Авторизация | Без авторизации, общий доступ по ссылке |
| Количество проектов на старте | 5-10 проектов — боковая навигация со списком проектов |

## 10. Оставшиеся риски

| Риск | Статус |
|------|--------|
| Агент может не успевать обновлять статусы в реальном времени — нужна очередь / буфер? | Риск (мониторить на старте) |
| При большом количестве задач канбан-доска станет неудобной — нужна виртуализация / пагинация? | Риск (вторая версия) |

## Следующий шаг для сборки прототипа

1. **Выбрать стек:** рекомендуется Next.js (SSR + API routes) + PostgreSQL + Prisma + WebSocket (или SSE) для real-time.
2. **Спроектировать схему данных:** Project → Subproject → Task, User, Status.
3. **Реализовать REST API** для CRUD задач и проектов.
4. **Сделать канбан-доску** с тремя колонками и карточками.
5. **Подключить real-time** (WebSocket/SSE) для обновления статусов от агента.
6. **Адаптировать агента** project-manager для вызовов API вместо записи в Markdown.
